# Specs, task tokens and token cards

*Status: proposal, for discussion. Nothing here is implemented. Revised once after review; the
changes are listed at the end.*

An agent reaches the world through the command-line tools it already knows — `git`, `gh`,
`curl`, a mail client, a calendar client, a taxis client — and through nothing else. It holds no
credential. Every request it makes goes through kleis, which decides it and attaches the
credential it needs. What an agent may do is written once, in kleis, as a **spec**; the agent is
handed a **token** naming that spec, and a **token card** telling it, in prose, what the token
lets it do.

Orchestra, the system that runs agents, takes part in exactly one way: it obtains a token for each
task, hands it to the sandbox together with what kleis says the sandbox needs, and revokes it when
the task ends. It does not know which services a token reaches.

This document specifies the kleis side (Part A), the orchestra side (Part B) and the supporting
work in other repositories (Part C). Part D lists what is deliberately left out, Part E the open
questions, Part F what the review changed.

## Terms

| term | meaning |
| --- | --- |
| **account** | A credential kleis holds for one service, installed by its owner, bound to the hosts it may be spent on: `mail/christian`, `zulip/christian@zulip.merten.dev`. |
| **spec** | A named, declarative description of what a bearer may do: which accounts, with which operations, under which conditions. Written in the spec language (A.3) and compiled into grants. |
| **token** | A biscuit signed by kleis's root key. A *bearer token*: holding it is the whole proof. |
| **task token** | A token made for one task by `derive` (A.7): a short expiry, the task's facts, an optional narrowing; revocable on its own. |
| **source** | What a task token is made from: a spec name, or a token handed in. |
| **token card** | Plain text, generated by kleis from a token, saying what the token lets its bearer do. |
| **extension** | Everything kleis knows about one kind of service: its manifest, the vocabulary specs may use for it, the prose cards are written in, what a sandbox needs to talk to it. |
| **identity** | Orchestra's: a persistent someone a task can be — name, standing instructions (`AGENTS.md`), memory — which now also names a source. |

## The example used throughout

A *secretary* identity: its own instructions (its role, the rules it follows), and access to
Christian's mail and calendar — reading and filing mail, sending only within `merten.dev`, and
keeping one calendar.

# Part A — kleis

## A.1 What exists today, and what changes

Today a token's authority block names grants: `grant("orchestra-github")`. A grant is a file an
operator writes; it names a service, the credentials it may spend, and datalog that decides each
request. An *issuer* — orchestra — mints tokens over HTTP (`/.kleis/v1/tokens`), naming grants
and stating facts within limits its configuration sets, and revokes what it minted.

This proposal adds:

1. **account host binding** (A.2);
2. **specs**, written in a small language and compiled into grants at load time (A.3–A.5);
3. **`spec(name)`** in a token's authority block, resolved to the spec's grants per request (A.6);
4. a **`derive`** endpoint that makes task tokens (A.7);
5. **setup** and **card** endpoints (A.8, A.9);
6. **extensions**, packaging per-service knowledge (A.10, A.11).

Grants, manifests, credentials, issuers, `/tokens` and `/revoke` keep working unchanged. A spec is
a way of writing grants, not a replacement for them.

## A.2 Accounts

An account is an existing kleis credential with one addition, the hosts it may be spent on:

```toml
name        = "zulip/christian@zulip.merten.dev"
service     = "zulip"
hosts       = ["zulip.merten.dev"]          # new
secret_file = "/run/kleis-secrets/zulip_christian"
```

* `hosts` lists exact host names; no wildcards.
* It is **required** when the service's extension has dynamic hosts (Zulip, CalDAV: A.10), and a
  credential without it is a load error there. For a service with a fixed host set (GitHub, mail)
  it defaults to the manifest's credential hosts, as today.
* It is enforced where the existing confinement is: `Credential.Record` gains `hosts`, and the
  reach check (`Manifest.mayCredentialReach`, at injection and after every redirect) requires the
  host to be in both the manifest's credential hosts and the account's. Whatever a grant derives,
  one server's key never goes to another.

An identity may have any number of accounts per service, including none.

## A.3 The spec language

A spec is a file, `config/specs/<name>.kleis`. The secretary:

```
spec secretary
  description "Reads and files Christian's mail and keeps his calendar."
  max_ttl 24h

  account mail/christian
    allow read, flag, move
    allow send where recipient all ends_with "@merten.dev"

  account caldav/christian@dav.example.org
    allow read
    allow write, delete where path starts_with "calendars/christian/personal/"
```

### Grammar

```
spec      ::= "spec" NAME NL field* block*
field     ::= "description" STRING NL
            | "max_ttl" DURATION NL
block     ::= "account" CREDENTIAL NL rule*
            | "grant" GRANT NL                     -- include an existing grant as is
rule      ::= "allow" ops ("where" cond)? NL
            | "datalog" BLOCK_STRING NL            -- escape hatch
ops       ::= OP ("," OP)*
cond      ::= atom ("and" atom)*
atom      ::= FIELD test                           -- single-valued fields
            | FIELD ("all" | "any") test           -- multi-valued fields
test      ::= "is" VALUE | "in" LIST
            | "starts_with" STRING | "ends_with" STRING | "matches" STRING
            | "<" VALUE | "<=" VALUE | ">" VALUE | ">=" VALUE
```

Indentation delimits blocks. `#` starts a comment. Names, strings and lists are as in TOML.

### Meaning

* An **`account` block** is one grant. It spends exactly that credential, for requests to the
  credential's service and hosts.
* **`allow OPS`** admits a request whose operation is one of `OPS`. Operation names come from the
  extension (A.10): a manifest operation (`send`, `set_flags`) or a group the extension defines
  (`read` = every operation that changes nothing).
* **`where COND`** narrows that line: the request is admitted by the line only if every atom holds.
  Fields come from the extension, which says which fact carries each and whether it is
  single-valued (`path`, `stream`: at most one fact per request) or multi-valued (`recipient`: one
  fact per value).
  * On a single-valued field the test applies to its value; a request with no value fails it.
  * On a multi-valued field the test is quantified. `all`: there is at least one value, and every
    value passes. `any`: at least one value passes. An unquantified test on a multi-valued field
    is a load error.
* Several `allow` lines in one block are alternatives: a request is admitted if any line admits it.
* Anything no line admits is refused. There is no `deny`: a spec lists what is allowed.
* **`grant NAME`** includes an existing grant file unchanged, for policy the language cannot say
  yet (the GitHub orchestra grant, at first).
* **`datalog '''…'''`** inside an account block adds raw rules and checks to that block's grant.
  The card quotes it verbatim (A.9).
* **`max_ttl`** bounds every token naming the spec. A token reaching an included grant is also
  bounded by that grant's `max_lifetime`; the effective bound is the minimum.

### Load-time checks

A spec failing any of these is not loaded, and kleisd refuses to start, as for a bad grant:

* every credential exists, its service has an enabled extension, and its `hosts` satisfy A.2;
* every operation and field is in that extension's vocabulary, and every value has the field's
  type;
* no two account blocks in one spec spend the same credential;
* within one account block, an `all` condition on a field may appear only on lines whose
  operations no other line of the block names (A.4 explains why);
* `max_ttl` is present.

## A.4 Compilation

Each account block compiles into one grant named `<spec>/<credential>`, with `service` and
`credential` set from the account:

```
check if spec("<spec>");
check if request_host($h), [<account hosts>].contains($h);

allowed(<n>) <- <ops test>, <conditions>;          // one rule per `allow` line, numbered
check if allowed($x);
<rejects>                                           // one per `all` condition
allow if true;
```

* `<ops test>` is `operation($op), [<operations, groups expanded>].contains($op)`.
* A single-valued condition is the field's fact and the test on its variable:
  `path($p), $p.starts_with("calendars/christian/personal/")`.
* `any` is the fact and the test: `recipient($a), $a.ends_with("@merten.dev")`.
* `all` is two parts. The line's rule requires a value (`recipient($a)`), and a reject refuses any
  value that fails the test:
  `reject if <ops test>, recipient($a), !$a.ends_with("@merten.dev");`
  A reject applies to the whole grant, not to one line. That is why the load-time check confines an
  `all` condition to operations no other line names: there is then exactly one line it could
  belong to.

The secretary's mail block compiles to:

```
// grant "secretary/mail/christian", service "mail", credential "mail/christian"
check if spec("secretary");
check if request_host($h), ["kleis-mail"].contains($h);
allowed(0) <- operation($op), ["list_mailboxes", "list_messages", "read_message",
                               "set_flags", "move_message"].contains($op);
allowed(1) <- operation($op), ["send"].contains($op), recipient($a);
check if allowed($x);
reject if operation($op), ["send"].contains($op), recipient($a), !$a.ends_with("@merten.dev");
allow if true;
```

`kleis spec compile <name>` prints the result, so what a spec means can always be read in the
language kleis evaluates.

## A.5 Specs and the existing grant machinery

A compiled grant is an ordinary `Policy.Grant`: everything in DESIGN §4 applies to it unchanged —
the guards the authorizer adds, one grant at a time (`Policy.Select`), credential choice
(`derivedCredentials`), the audit record. The audit record names the compiled grant and the spec's
source hash, so a decision can be replayed against the spec that made it.

The vocabulary of compiled grants (the predicates their rules derive, such as `allowed`) is added
to what `Token.mint` already refuses as extra facts, as the vocabulary of grant files is today.

## A.6 `spec(name)` in a token

A token's authority block may contain `spec("<name>")` facts as well as `grant("<name>")` facts.

Resolution per request replaces step 2 of today's selection and leaves the rest alone:

1. verify the token against the root key, and every block's revocation id against the list;
2. read `spec(…)` and `grant(…)` from the **authority block only** (`authorityStrings`);
3. the candidate grants are the named grants, then the compiled grants of each named spec, in the
   order the token names them;
4. keep the candidates whose service is the manifest claiming the request's host;
5. try them one at a time, as today.

If no candidate remains, the refusal says so: *"the spec `secretary` has no account for `zulip`"*.

### Why resolution is per request

The token names the spec; the spec file says what the spec allows *now*. Editing a spec changes
every outstanding token naming it, without reissuing any: access is declared in a reviewable file,
not inside an opaque bearer token. The consequence — a card read at the start of a task can go
stale if the spec is edited during it — is addressed in A.9.

### What cannot forge or widen it

* `spec` is read from the authority block only, which only the root key signs.
* `spec` joins `Token.reservedPredicates`: no issuer may state it as an extra fact. An issuer
  obtains a spec only through its configuration (A.7.1).
* Every compiled grant begins `check if spec("<spec>")`, so it cannot be reached by naming it as a
  grant.
* Anyone holding a token can append blocks, and any biscuit library will let them put facts and
  rules in one — kleis's own `attenuate` refuses to, but nothing else need. Such facts cannot widen
  anything: biscuit evaluates the grant's rules and checks trusting only the authority block and
  the authorizer, so an appended `spec(…)`, `operation(…)` or `allowed(…)` is invisible to them, and
  `derivedCredentials` ignores a `use_credential` that does not come from those two. What an
  appended block *can* do is add checks, which only refuse.

## A.7 Task tokens: `derive`

### A.7.1 Issuer configuration

```toml
[[issuer]]
name       = "orchestra"
grants     = ["orchestra-*"]          # as today
facts      = ["task_*"]               # as today
specs      = ["worker", "secretary"]  # new: the specs it may derive task tokens from
max_ttl    = "24h"
token_file = "/kleis/issuers/orchestra.token"
```

### A.7.2 `POST /.kleis/v1/derive`

Authenticated with an issuer's credential, as `/tokens` is. Two forms.

**From a spec** — the main path:

```json
{ "spec":   "secretary"
, "ttl":    "6h"
, "bearer": "orchestra:t-5678"
, "facts":  [ { "name": "task_id", "terms": ["t-5678"] }, … ]
, "narrow": ["mail: only read, flag"]
}
```

kleis checks the spec is in the issuer's `specs`, vets the facts exactly as `/tokens` does today
(the issuer's `facts` patterns, `reservedPredicates`, every manifest's vocabulary and every grant's
and compiled grant's rule heads: `Token.mint`), and issues a new token whose **authority block** is
written by kleis:

```
spec("secretary");
bearer("orchestra:t-5678");
issued_by("orchestra");
task_id("t-5678");
…                                                   // the vetted facts
check if time($t), $t < <now + min(ttl, issuer max_ttl, spec max_ttl, included grants' max_lifetime)>;
<narrowing checks>                                  // A.7.4
```

This is today's `/tokens` with `spec(…)` in place of grant names: the task facts sit in the
authority block, where existing grants — the GitHub orchestra grant — already read them. Nothing
about trust, scopes or credential choice changes.

**From a token** — for a task handed a token explicitly:

```json
{ "token": "<a token>", "ttl": "6h", "narrow": [ … ] }
```

kleis verifies the token (root key, not revoked, not expired), refuses it if its authority block
contains `issuer(…)` — an issuer credential is not a source — and appends **one block containing
only checks**: the expiry and the narrowing. It adds no facts: the token reaches exactly what it
reached, minus what the block refuses. A grant that needs task facts (the GitHub one) therefore
does not apply to a token-sourced task, which is the point — the token's holder decided what it
reaches, not orchestra. (Task facts on token-sourced tasks would need third-party blocks and
changes to `derivedCredentials`; Part D.)

Either form returns:

```json
{ "token": "…", "revocation_id": "…", "expires": "…", "card": "…" }
```

`revocation_id` is the one id that distinguishes this task token: the new authority block's id
from a spec, the appended block's id from a token. kleis records the task token against the issuer
with that id alone, so `/revoke` with it revokes this copy and nothing else — never the source
token. (Revocation is checked against every block's id, so revoking a source revokes every copy
derived from it.)

### A.7.3 What `bearer` is

From a spec, `bearer` is the authority fact, as in `/tokens`. From a token, it is kept in the
issued record only (for listing and the audit log); no fact is added.

### A.7.4 Narrowing

A narrowing is written per service in the `allow` syntax:

```
mail: only read, flag
caldav: only read
```

and compiles to rejects, not checks:

```
reject if request_service("mail"), operation($op), ![<read>, "set_flags"].contains($op);
reject if request_service("caldav"), operation($op), ![<read>].contains($op);
```

`request_service(name)` is a new primitive fact: the name of the manifest that claimed the
request. A reject fires only on a request to that service, so the token still holds everywhere
else — including at the admin endpoints and passthrough, where `tokenHolds` evaluates a token's
checks with no request facts at all, and where a `check if request_service(…)` would have failed.

A service the narrowing does not mention is not narrowed. Groups are expanded at derive time; a
spec edited during the task does not change the narrowing.

## A.8 `GET /.kleis/v1/setup`

Authenticated with any token, by its bearer. It returns what a sandbox needs to use the token with
ordinary tools, assembled from the extensions of every service the token reaches:

```json
{ "proxy":    { "ca_pem": "…" },
  "env":      { "GH_TOKEN": "kleis", "GIT_CONFIG_COUNT": "1", … },
  "files":    [ { "path": ".zuliprc", "mode": "0600", "content": "…" },
                { "path": ".config/khal/config", "content": "…" } ],
  "no_proxy": [],
  "card":     "…" }
```

* Files and environment hold **no secrets**. Where a client insists on a credential, the extension
  supplies a placeholder kleis strips and replaces (`GH_TOKEN=kleis`, a zuliprc with `key=kleis`).
* `path` is relative to the sandbox user's home: no leading `/`, no `..` segment. kleis refuses to
  produce anything else, and a consumer (B.2.3) must refuse it too.
* `env` may not set the proxy, CA or `NO_PROXY` variables; those are the consumer's.

`kleis setup --token T` (which exists, for proxy and CA) grows to print the same.

## A.9 Token cards

### Content

```
This token acts as "secretary": Reads and files Christian's mail and keeps his calendar.
It expires 2026-10-11 18:00 UTC.

Mail — christian@merten.dev (kleis-mail; `kleis-mail --help`)
  • list, read, flag and move messages in any mailbox
  • send mail, only if every recipient's address ends with "@merten.dev"
  • nothing else: deleting is refused

Calendar — dav.example.org (khal and vdirsyncer are configured)
  • read every calendar
  • create, change and delete events whose path starts with "calendars/christian/personal/"

This copy is narrowed further: mail — only read and flag.

Anything else is refused with HTTP 403, and the response says which rule refused it.
```

For a worker task, the GitHub section carries what today's prompt does (`Orchestra/Kleis.lean`
`systemPrompt`): its fork, its upstream, the issue it was launched from, the labels its pull
requests carry, where it may push.

### How it is produced

* The heading is the spec's `description`; the expiry is the earliest among the token's checks.
* Each account is a section, headed with the account's display name and the extension's client
  hint, with one bullet per `allow` line: the extension's phrase for the operations, then each
  condition rendered from the field's and the test's phrases.
* **Task facts** are rendered by the extensions that use them: an extension's `extension.toml` may
  phrase facts (`task_fork(o, r)` → "your fork is o/r"), and the card includes every phrased fact
  present in the authority block, under the section of the extension that phrased it. This is how
  the GitHub guidance moves from orchestra into kleis.
* `grant` includes and `datalog` blocks are rendered as their source under *"also, as written:"*.
* Narrowings are listed after the sections.
* Passthrough hosts reach no account and are not described.

### Where it is served

In the `derive` response; in the `setup` response; and at `GET /.kleis/v1/card`, to any bearer,
for its own token. The card reflects the spec as it is when asked, so an agent unsure whether its
card is current can re-read it.

## A.10 Extensions

An extension is a directory, `extensions/<service>/`, shipped in the kleis repository and image:

```
extensions/zulip/
  manifest.toml        # as today, without `hosts` when the hosts are dynamic
  extension.toml       # vocabulary, card phrases, setup
  README.md
```

`extension.toml`:

```toml
service = "zulip"
display = "Zulip"
client  = "the `zulip` CLI and the Python `zulip` package (~/.zuliprc is configured)"
hosts   = "dynamic"            # claimed from accounts; or "fixed": the manifest's

[groups]
read  = ["read", "events"]

[operations]
send_message = "send messages"
edit_message = "edit messages it sent"
react        = "add and remove reactions"

[fields.stream]
fact   = "stream"
type   = "string"
values = "single"
phrase = "to the stream"

[facts]                        # task facts this extension renders on cards (A.9)

[setup]
files = [ { path = ".zuliprc", mode = "0600",
            content = "[api]\nemail=kleis\nkey=kleis\nsite=https://{host}\n" } ]
```

`{host}` and similar placeholders are filled per account. For an extension with dynamic hosts,
kleis claims every host an account of that service is bound to, plus any the operator lists:

```toml
extensions = ["github", "zulip", "caldav", "mail"]

[extension.zulip]
hosts = []   # further hosts to claim without an account, so a request there is refused with a reason
```

## A.11 The first extensions

| service | transport | operations (groups) | fields | sandbox setup |
| --- | --- | --- | --- | --- |
| github | HTTPS, git | existing manifest | existing; task facts phrased for the card | `GH_TOKEN=kleis`, git proxy auth |
| zulip | HTTPS | read, events, send_message, edit_message, delete_message, react, update_flags, typing, upload, subscriptions | `stream`, `message_type` (single) | `.zuliprc` placeholder |
| caldav | HTTPS (WebDAV) | read, write, delete, manage | `path` (single) | vdirsyncer and khal configs |
| mail | HTTP, via kleis-mail | list_mailboxes, list_messages, read_message, set_flags, move_message, send | `mailbox`, `move_target` (single), `recipient` (multi) | none |
| taxis | HTTPS | from taxis's API | `project` (single) | taxis CLI config, placeholder token |

### Mail

Mail is not HTTP, so the mail extension includes **kleis-mail**, a small HTTP service that speaks
IMAP and SMTP on a request's behalf, and a CLI, `kleis-mail`, for agents.

* kleis-mail holds no credential and knows no server. kleis injects the account — one line of JSON:
  user, password, IMAP and SMTP `host:port`, optional `from` — as a request header, after stripping
  any copy the client sent. Reached without kleis, it does nothing.
* It runs beside kleisd, reachable only by kleisd; the manifest claims its address and allows
  plain HTTP to it (`allow_plaintext`), since the hop never leaves the host.
* The manifest emits `recipient(a)` once per address in `to`, `cc` and `bcc` (a manifest rule over
  the flattened body, as the prototype does). The gateway accepts those three fields only as arrays
  of bare lower-case addresses, so what kleis reads is what is sent.
* A prototype exists (chrisflav/nixos-config#38, `modules/kleis/mail-gateway.py`), tested through
  kleis for header injection, stripping and refusals, not yet against a real IMAP server.

# Part B — orchestra

## B.1 What orchestra does today

Orchestra mints a token per task through `/tokens`, naming the grants in its configuration
(`kleis.grants`, default `["orchestra-github"]`) and stating `task_*` facts (`Kleis.lean`). It puts
the token in the sandbox's proxy URL, sets `GH_TOKEN=kleis` and git's proxy-auth configuration,
adds a GitHub section to the system prompt, hides its GitHub MCP tools, and revokes the token when
the task ends.

## B.2 What it does instead

### B.2.1 Configuration

The `kleis` block keeps `url`, `proxy`, `issuer_token`/`issuer_token_file`, `ca_file`,
`no_proxy`, `ttl` and `push_prefix` (the source of `task_push_prefix`), and gains:

| key | default | |
| --- | --- | --- |
| `default_spec` | none | the spec a task with no other source runs under — e.g. `"worker"` |

`grants` remains during the transition (B.5) and is then removed.

### B.2.2 A task's source

A task resolves one source at launch. The first that is set wins:

1. the task's `kleis_token` — a `{{secret}}` reference, resolved from `secrets.json` at launch and
   never stored in the queue (the precedent is the identity's `taxis_token`);
2. the task's `kleis_spec`;
3. its identity's `kleis_spec` or `kleis_token`;
4. its role's, then its listener action's, `kleis_spec`;
5. `kleis.default_spec`;
6. none: the task runs with no kleis token, as a task does today when `kleis` is unset.

The identity comes before the role: a secretary task dispatched for a role keeps the secretary's
access. A role or listener action that wants less sets `kleis_narrow` instead, which every level may
carry and which accumulates — each level's narrowing is applied, so the result is their
intersection.

The secretary's identity:

```
identities/secretary/identity.json   {"name": "secretary",
                                      "description": "Christian's secretary",
                                      "kleis_spec": "secretary"}
identities/secretary/AGENTS.md       its role and rules
```

### B.2.3 At task start

1. `POST /.kleis/v1/derive`:
   * from a spec: the spec, the task's `ttl`, `bearer = "orchestra:<task id>"`, the narrowings,
     and the task facts orchestra states today — `task_id`, `task_identity`, and for a task on a
     repository `task_fork`, `task_upstream`, `task_issue`, `task_tool`, `task_writable`,
     `task_pr_labels`, `task_label_any`, `task_org`, `task_push_prefix`. These describe the task,
     not a service: orchestra states what it knows and does not know which grants read them.
   * from a token: the token, the `ttl` and the narrowings.
2. `GET /.kleis/v1/setup` with the task token.
3. Launch the sandbox with the proxy URL carrying the task token; `setup.env`, after refusing any
   proxy, CA or `NO_PROXY` variable in it; `setup.files`, after refusing any absolute or `..` path,
   written without following symlinks under the sandbox home; the CA bundle (system roots plus
   `setup.proxy.ca_pem`, as today); `NO_PROXY` from configuration and `setup.no_proxy`.
4. Compose the system prompt: orchestra's own text, the identity's `AGENTS.md`, the **token card**,
   then the task prompt.

### B.2.4 At task end

`POST /.kleis/v1/revoke` with the `revocation_id` derive returned, in the `finally` that revokes
today.

### B.2.5 What is removed

* `Kleis.mint`, replaced by `derive`.
* `Kleis.systemPrompt`, replaced by the card.
* `GH_TOKEN=kleis` and the git proxy configuration in `Kleis.launch`, now GitHub's setup.
* The GitHub MCP tools (`create_pr`, `merge_pr`, `comment`, `label_issue`, `get_pr_comments`,
  `create_repository`, `refresh_token`), already refused under kleis.
* After C.1, the taxis MCP tools.

What remains as MCP tools is orchestra's own: `queue_task`, `get_task_input`,
`submit_task_output`, `health`.

## B.3 Spawned tasks

A task spawned through `queue_task` inherits its parent's identity today. It also inherits its
parent's **source** — the spec name, or the `{{secret}}` reference of the token — and its
narrowings, and derives its own task token when it is dispatched, like any task. It does not
derive from the parent's task token: the parent's token is revoked when the parent ends, which may
be before the child is dispatched, and the queue holds no live token.

A child may add narrowing of its own (accumulated as in B.2.2) but may not choose another source.
Its task facts are its own — another repository or other tools, as `queue_task` allows today,
within the spawn policy that bounds them now.

## B.4 What orchestra does not do

It does not know which services a token reaches, holds no account credential and no biscuit code,
and does not interpret setup files or cards beyond the path and variable checks in B.2.3.

## B.5 Transition

1. kleis ships accounts' `hosts`, specs, `derive`, `setup`, `card` and extensions. `/tokens` is
   unchanged, so orchestra keeps working.
2. Write the spec `worker`: `grant orchestra-github`. The grant file is unchanged — under `derive`
   from a spec, the task facts are in the authority block, where it reads them today.
3. Orchestra switches from `/tokens` to `derive` with `default_spec = "worker"`, and the card
   replaces its GitHub prompt section.
4. Remove `kleis.grants`, `Kleis.mint`, the GitHub prompt and launch code.

# Part C — supporting work

## C.1 A taxis CLI

taxis has no command-line client (its repository holds the server and a Claude plugin with two
skills). One is needed before orchestra's taxis tools can go: a `taxis` executable in the taxis
repository, built on `Taxis/Client.lean`, reading its server URL and token from a config file the
taxis extension's setup writes, with a placeholder token kleis replaces. Then a taxis extension in
kleis, and an identity's `taxis_token` becomes a kleis account.

## C.2 Deployment (nixos-config)

The kleis NixOS module declares accounts as credentials with `secret_file`s from sops and their
`hosts`; installs spec files from the host's directory; lists the enabled extensions and runs
kleis-mail beside kleisd when mail is enabled; and gives the orchestra issuer its `specs`.
chrisflav/nixos-config#38 is superseded; its mail gateway moves into kleis.

## C.3 Orchestra configuration

`identities/<name>/identity.json` gains `kleis_spec` (or `kleis_token`). Tasks, roles and listener
actions may carry `kleis_spec` and `kleis_narrow`.

# Part D — not in this proposal

* **Task facts on token-sourced tasks.** Would need third-party blocks signed by an issuer key,
  grants written `trusting authority, <issuer key>` throughout, and `derivedCredentials` widened
  to trust that key's blocks. Not needed while orchestra's own tasks derive from specs.
* **Orchestra's daemon through kleis.** Listeners, triage, the merger and workspace cloning keep
  their own credentials for now; later the daemon gets a spec of its own.
* **Orchestra's API behind kleis**, which would turn `queue_task` into a CLI call.
* **Account ownership**: who may write a spec using whose accounts. Today the kleis operator
  writes every spec.
* **An IMAP/SMTP transport** in kleis. kleis-mail is sufficient.

# Part E — open questions

1. **Inline specs.** Should `kleis token issue --spec FILE --inline` compile a spec into the token
   itself, for a self-contained token whose meaning cannot change? Useful outside orchestra.
2. **Card staleness.** Is "re-read `/card` when unsure" enough, or should a spec edit revoke
   outstanding task tokens naming it?
3. **Language scope.** Is `allow … where …` with `and`, the listed tests and `all`/`any` enough for
   the first extensions, with `datalog` as the escape hatch?
4. **Task fact names.** `task_fork`, `task_pr_labels` and the rest are what orchestra knows about
   its task, but their shape follows GitHub. Should they become generic (`task_repository`,
   `task_labels`) with the GitHub extension mapping them?

# Part F — what the review changed

An adversarial review against the kleis, lean-biscuit and orchestra sources found three blockers
and several major issues in the first draft. Changes:

* **Task facts in the authority block, not a third-party block** (was A.7.2–A.7.4). `derivedCredentials`
  (`Policy/Authorize.lean`) only honours `use_credential` from the authorizer and block 0, and an
  explicit `trusting <key>` replaces the default scope, so moving the GitHub grant's facts into an
  issuer-signed block would have stopped it spending any credential. kleis writes the authority
  block of a spec-derived token itself, so the facts can stay where they are today. Issuer signing
  keys and the `trusting issuer(…)` rewrite are dropped (Part D).
* **Narrowing compiles to `reject if`, not `check if`** (A.7.4). `tokenHolds` (`Proxy/Forward.lean`)
  evaluates a token's checks with only `time` present — at the admin endpoints, for passthrough and
  per session — so a `check if request_service(…)` would have locked a narrowed token out of
  `/setup`, `/card` and passthrough.
* **Spawned tasks derive from the parent's source, not its task token** (B.3). Otherwise a queued
  child dies when the parent's token is revoked, sees the union of both tasks' facts, and requires
  the queue to hold a live token.
* **One `revocation_id` per task token** (A.7.2). Orchestra revokes one id; kleis's `revokeFor`
  revokes every id in a record, which could have revoked the source token.
* **Derive from a token adds checks only, refuses issuer credentials** (A.7.2).
* **Fact vetting as in `Token.mint`**, plus compiled grants' vocabulary (A.5, A.7.2).
* **`all` via `reject if` over one fact per value** (A.4). The array form had a bypass — `to`, `cc`
  and `bcc` are separate captures — and biscuit has `reject if`, so negation was never the obstacle.
* **Account `hosts` required for dynamic-host services, exact names only, enforced at injection**
  (A.2).
* **Cards render task facts through extensions** (A.9), so the GitHub guidance orchestra's prompt
  gives today is not lost.
* **Lifetimes** take the minimum of task, issuer, spec and included grants' bounds (A.3, A.7.2).
* **Setup paths and variables are restricted** on both sides (A.8, B.2.3).
* **Precedence**: identity before role; roles narrow rather than replace (B.2.2).
* **A.6 states what actually stops an appended block** — default scope and `derivedCredentials` —
  rather than claiming blocks can only add checks.
